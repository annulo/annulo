# 项目的版本：本地 git

项目是一个 git 仓库，改动历史都在 git 里。下面提到 creght 的只对**在线项目**（项目在 creght 上）适用；离线项目的 `annulo push` 只在本机提交。

- **什么时候要推**：页面、本机函数、表声明、任务、skill 都在本机生效，保存就行（左侧页面自动刷新，表按 `tables/` 自动补建）。
  在线项目的 **`backend/func/*.ts` 跑在 creght 平台上，改了必须推**，不推的话平台用的还是旧代码。另外，要存档、同步到别的设备或给别人时也要推。
- **`annulo push -m '为什么改'` 做了什么**：先提交；在线项目再看远端，有编辑器或其他设备的改动就先合进来、单独提交，再推到预览，不会强推。报冲突就改掉文件里的冲突标记，再重跑。
- 每轮对话结束，Annulo 会自动提交一次；你也可以自己 `git commit`。

## 升级模板

用户让你升级项目的模板（「帮我升级」「升到最新版」）：先 `annulo template` 看当前基于哪一版、新版本改了什么、这台 Annulo 够不够新，
再 `annulo template upgrade`（和 设置 → 项目 里点「升级」是同一条路）。合并干净就完成了；有冲突时合并停在进行中，命令会列出冲突的文件，照下面解完、提交就完成升级。
升级前有没提交的改动会先自动提交，不用你先清。

## 解冲突

模板升级、换模板时 git 合并会出冲突（`<<<<<<< HEAD` / `>>>>>>> template`），推送时和远端改动也会出冲突（`<<<<<<< local` / `>>>>>>> remote`）。

先看两边各改了什么：模板那边用 `git log template`、`git diff <上一版模板>..template -- <文件>`，项目这边用 `git log -- <文件>`；推送冲突里，远端改的就是标记里 remote 的那部分。

- 两边各改了一小处、互不矛盾（比如模板加了功能，项目改了文案、配置），**合在一起，两边都保留**。大多数冲突是这种。
- 一边把整个页面、文件改成了别的用途，或者两边的改法互相矛盾、拼在一起跑不起来，**不要自己选**：
  用 `request_user_input` 把选项摆给用户，说清保留哪一边、各自会怎样（比如「用模板的：这个页面变回原来的功能，你改成的那个页面就没了」），按用户选的改。
- 在线项目的推送冲突也可以整份取一边：`creght resolve <文件> --ours`（本机）/ `--theirs`（远端）只处理冲突的那几段，不冲突的远端改动已经合进来了；
  要整份用某一边，就 `git checkout <提交> -- <文件>`，或者照那一边重写。

改完用 `grep -rn '^<<<<<<<\|^>>>>>>>' .` 确认没有标记了，再 `annulo push`；推送时又撞上新的远端改动，就照样再解一轮。

## 看历史、回滚

- 都用 git：`git log`、`git diff`、`git revert <提交>`、`git checkout <提交> -- <文件>`，然后 `annulo push`。在线项目也不要用 `creght version rollback` 回滚项目。
- 用户说模板带的页面、功能坏了，想「变回原来的样子」：可以 `git checkout template -- <文件>`；用户自己也能在 设置 → 项目 →「恢复模板文件」里勾选文件，换成模板最新版（能撤销）。
- **git 只管代码。** 业务表里的数据、外部平台上的内容和配置，回滚代码时不会跟着回去。回滚前告诉用户这一点，数据要改就另外改。
- 项目对外的网站（比如 creght 站点）不在这个仓库里，也不用 `annulo push`，按它自己的工具推。
